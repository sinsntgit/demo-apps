Getting started

OntoStudio builds an ontology for any domain: a precise, shared description of the things a business deals with (its classes), how they relate (its relationships), what is recorded about them (their attributes) and the rules that hold. It researches the published industry standards for the domain, builds on them, explains the result in plain language, draws it, lists the questions it can answer, and lets you test whether it really covers a use case.

The flow in six steps

  1. Create an ontology: copy a ready-made one from the Pre-built library, or build a new one from a domain, your use cases and requirements, a database, or a folder of documents — any one of them is enough. See Creating an ontology.
  2. Build it with an AI model. This takes a few minutes and runs in the background.
  3. Read the Overview and the Standards it was built on; look at the Diagram.
  4. Adjust it — by clicking on the diagram, in the tables, or by telling the AI what to change.
  5. Test it: enter use cases in the Test bed, run the reasoner and the gap review, close the gaps.
  6. Download it as a handbook (PDF), a presentation (PowerPoint), a workbook (Excel) or as OWL / Turtle / JSON-LD / JSON for other systems. See Downloads.

A sample ontology, Sample: Retail order management, is installed with the application so that every screen can be tried before an AI model is set up.

What an ontology is — the words used here

TermMeaningExample
ClassA kind of thing.Order, Customer, Shipment
Subclass (“is a kind of”)A more specific class. It inherits every relationship and attribute of its parent.Store is a kind of Sales channel
ModuleA subject area that groups classes. Each module has its own colour in diagrams.Parties, Product catalogue
RelationshipA named link from one class to another. Read it as a sentence.Order — placed by → Customer
InverseThe same link read the other way round.places ↔ placed by
AttributeA value recorded about a class.Order has order date (date and time)
How many (cardinality)Whether the relationship or attribute is optional or mandatory, and whether there can be several.“exactly one (mandatory)”
Controlled valueOne of a fixed list of allowed values.Order status: Placed, Paid, Shipped…
RuleA business constraint or calculation in a plain sentence. A “never overlap” rule is also checked by the reasoner.A shipment needs a paid order.
Use caseA question or task the ontology must be able to answer (a “competency question”).Which paid orders have not shipped?
Standard / alignmentA published ontology or industry standard the model builds on; a class can be declared the same as, a kind of, or related to a published term.Order = schema:Order

The method follows standard practice in ontology engineering: reuse published vocabularies first, let the use cases decide what must be in the model, check it with a reasoner, and keep every version.

What these are — and are not

They are starter models written for this application. Each condenses the core concepts of the published standards for its industry and says which standards it follows. They are not the official standards themselves: the official FIBO or FHIR, for example, are far larger. If you need an official ontology in full, download it from its publisher and bring it in with ⬆ Import file. The alignment notes were written from knowledge of the standards, not checked term by term against them — verify before you publish.

Adding your own ontologies to the pre-built library

The library is a folder of plain-text files (library/*.onto) on the server; an administrator with access to the server can add a file in the same simple format and restart the application. The format is described at the top of app/library.py. A file with a mistake is skipped and reported in the server log; it never stops the application.

Creating an ontology

In the library press ＋ New ontology. The wizard has four steps; only the name is mandatory, and you may give as little or as much as you have. (To start from a ready-made model instead, see Pre-built library.)

1 · Basics

  • Domain — what the ontology is about, in a few words. Leave it blank to let the AI infer it from your documents or database.
  • Scope — what to cover and what to leave out. The more precise, the better the result.
  • Size — Compact (about 15–25 classes), Standard (about 35–55) or Comprehensive (about 70–100; slower and costs more).
  • Folder — where it is kept; see Folders & access.

2 · Use cases & requirements

This is how you get a custom ontology designed around your needs.

  • Use cases it must answer — one per line, in your own words. Each becomes a required use case: the ontology is designed so that it can answer it, it is listed first under Use cases with the label “Required by the owner”, and you can test it with one click.
  • Requirements — anything it must satisfy: regulations, systems it must map to, naming rules, level of detail.
  • Reference notes — your own terms, glossary and abbreviations.

3 · Database & documents

Optional. Ground the ontology in what you already have — see Building from a database or documents.

4 · Build

Choose the AI model and how many extra use cases the AI should write, then press ✨ Create and build with AI. Create empty makes an ontology with nothing in it, to draw by hand on the diagram.

What happens during a build

  1. Reading the source material — database structure and documents.
  2. Researching industry standards — candidates are picked from the built-in catalogue of 65 published ontologies and standards (schema.org, FIBO, HL7 FHIR, GS1, ISO 20022, SKOS, PROV-O and so on); the AI chooses those that fit, says how each is used, and may add others it knows.
  3. Designing the class hierarchy on top of those standards.
  4. Adding relationships, attributes, controlled values and rules.
  5. Completeness review — the draft is read critically against the scope and your use cases, and the gaps found are closed.
  6. Writing the explanation and the use cases.

If a build does not finish, the reason is shown and nothing is lost: press Build again, pick another model, or narrow the scope.

Importing an existing ontology file

⬆ Import file in the library brings in an OWL (RDF/XML), Turtle, JSON-LD or N-Triples file — for example a published standard or a model from Protégé — or a JSON file exported from this application. It becomes a normal ontology that you can extend, test and export. Classes, the hierarchy, properties with their domain and range, labels, definitions and individuals are read; complex logical expressions are not.

Data sources — build ontologies from your databases, datasets and documents

A data source is a database, or a set of uploaded datasets and documents, that you set up once on the Data sources page and then use for as many ontologies as you like — the way a data model is set up once in AskData. Its tables are profiled and its documents read when you set it up, so every ontology built from it starts from a precise picture of your data, not just table and column names.

Setting one up

＋ New data source, then choose:

  • Upload datasets and documents — then ＋ Add files: choose files, a whole folder, or drop them. You can mix:
    • Datasets — CSV / TSV, Excel (each sheet is a table), SQLite files (each table), JSON files holding lists of records. They are profiled, and a copy of each file is kept on the server so that knowledge graphs can be built from its rows (it is deleted with the file or the data source).
    • Documents — PDF, Word, PowerPoint, Markdown, text, JSON, XML, HTML, YAML, SQL scripts. Their text is kept.
    Uploading a file with the same name again replaces it and keeps the descriptions you wrote.
  • Connect a database — PostgreSQL, MySQL / MariaDB, SingleStore, Microsoft SQL Server, Oracle or Snowflake: host, database, user, password (for Snowflake: the account identifier from your Snowflake web address, e.g. orgname-accountname, plus the warehouse and, optionally, the role and schema; for Oracle the database is the service name). The driver for that kind of database must be installed on the server — see requirements-drivers.txt; if it is not, the message names the package to install. The password is stored encrypted so that ↻ Re-read database can profile it again later; it is never shown again. Use a read-only user. Each table is profiled from at most 2,000 rows; nothing is ever written to the database, and only queries built by the application are run.

Documentation — help the AI understand the data first

The Documentation tab (and the box on the New data source form) is where you explain the data before any ontology is built from it:

  • Notes — what the system is for, what the main tables hold, what codes and statuses mean, business rules, abbreviations; paste a data dictionary or glossary.
  • Documentation files — data dictionaries, system manuals, process descriptions, report specifications (PDF, Word, PowerPoint, Markdown, text, HTML, JSON, XML). For a database data source this is where documents go; datasets are refused there (they belong in a data source of uploaded files).

Both are given to the AI with the table profiles, as the authoritative explanation, every time an ontology is built from the data source.

✨ Describe with AI shows you what the AI understood before you build: it reads the documentation and the profiles and drafts a business description of every table and column that has none yet. The drafts are marked AI draft; check them in each table — saving makes them yours. Descriptions written by people are never replaced. It also lists the terms it found and what the documentation leaves unclear — worth adding to the notes.

What the profile contains

For every table: the number of rows, and for each column its type, how many values are empty, how many distinct values it has, whether it is unique, the range of numbers and dates, and its role:

RoleMeaningWhat it usually becomes in the ontology
identifierA key: unique, named like an id or code.The identifying attribute of a class.
referencePoints to another table's key — declared by the database, or inferred from names and values (e.g. dealer_id in one file matching id in dealers.csv).A relationship.
code listA small set of values, all listed with their counts (statuses, types, regions).A class with controlled values.
yes / noTwo values such as Y / N.A yes/no attribute.
date, measure, free text, attributeDates, amounts and quantities, long text, anything else.Attributes with the right datatype.

Columns that look like personal data (names, emails, phone, ID or account numbers, addresses, dates of birth) are marked; their values are not kept as samples unless the owner allows it.

Describe your data

Click a table to see its profile. Write what the table and its columns mean in business terms — these descriptions are given to the AI as the authoritative meaning, and make a noticeably better ontology. Untick a table to leave it out (tables that look like logs, staging, audit trails or backups are left out automatically).

Building an ontology from it

  • On a data source, press ✨ Build an ontology from this: the New ontology wizard opens with the data source chosen and its name filled in. Nothing else is required — the domain is inferred from the data — but use cases and requirements make the result sharper.
  • Or press ＋ New ontology: step 1 lists your data sources under Build from your data — tick any number. Data sources that are still empty are listed but cannot be ticked.
  • Or on an existing ontology's Sources tab, ＋ Add from the library; then rebuild.

The AI receives each included table's profile — with your descriptions, the references, the code lists and their values — and the text of the included documents (condensed first if there is a lot). It models business meaning, not storage: code lists become controlled values, references become relationships, technical columns are left out, and every class records the table or document it came from (Derived from, also in the Excel and OWL downloads). Up to about 100 documents per build work well.

Sample values and access

  • Share sample values with the AI model (on by default, per data source): a few example values per column and the full value list of code columns. Untick for statistics only.
  • Also for columns that look like personal data (off by default).
  • An administrator can stop all data sources sending values: Admin › Settings › Data sources.
  • Access: a data source is private to its owner and administrators until shared with named ontologists or with everyone who builds ontologies. Those people can build from it and read its profiles; only the owner and administrators can change, re-read or delete it. Viewers do not see data sources. If an ontology uses a data source someone has no access to, a build by that person is refused and says which one.
  • Keep a copy of uploaded datasets on this server (on by default, files only): needed to build knowledge graphs from their rows. Switching it off deletes the copies kept so far.
  • Load personal data into knowledge graphs (off by default): whether columns that look like personal data are loaded when a knowledge graph is built from this data source.
  • Deleting a data source unlinks it from its ontologies; what was already built stays.

Material added to one ontology

Besides data sources from the library, documents and database structures can be added to a single ontology — in the wizard (step 3) or later on its Sources tab. This is quicker for a one-off, but nothing is profiled and nothing is reused. It is read when the ontology is built: after adding or removing sources use ✨ AI › Rebuild from scratch.

Documents or a whole folder

  • Drop files or a folder onto the box, or use Choose files / Choose a folder (sub-folders are included).
  • Supported: PDF, Word, PowerPoint, Excel, CSV, text, Markdown, HTML, JSON, XML, YAML, SQL / DDL scripts, SQLite database files. Up to 25 MB per file and 300 sources per ontology.
  • The text is extracted and kept; the original file is not stored. For spreadsheets and CSV only the headings and the first rows are read, to show the structure.
  • Scanned PDFs (pictures of pages) contain no text and are reported as not readable.
  • A small set of documents is given to the AI in full. A large set is first distilled batch by batch into concepts, relationships, attributes, rules and questions, and the ontology is built from those findings. If the material is too large, the build log names the documents that were not read — nothing is dropped silently.

A database

Three ways, all of which read only the structure — tables, columns, types, keys and comments. No rows are ever read.

  1. Upload a schema script (.sql / .ddl) with the CREATE TABLE statements.
  2. Upload a SQLite file (.db, .sqlite).
  3. Read a live database: choose the type (PostgreSQL, MySQL / MariaDB, SQL Server, Oracle), host, database, user and password. The password is used for that one read and is not stored. A read-only user is enough. The driver for that kind of database must be installed on the server; if it is not, the message says which package the administrator has to install.

The AI models the business meaning, not the storage: a table describing a thing or event becomes a class with a business name, a pure link table becomes a relationship, a lookup table becomes a list of controlled values, a foreign key becomes a relationship, and technical columns are left out. Each class and property keeps a Derived from note naming the table or column it came from, so the mapping back to the database is preserved (it is in the Excel and OWL downloads too).

Reading the result: Overview and Standards

The Overview tab is the complete explanation of the ontology: what it is, its purpose, what is and is not covered, a walkthrough of how to read the model, a paragraph per module, and the design decisions with the reasons behind them. The six tiles at the top open the matching tab. ✎ Edit lets you correct the text; ✨ AI › Rewrite the explanation writes it again from the current model.

The Standards tab shows the published ontologies and industry standards the model builds on: how each is used, which terms are reused, and a table of every class that is aligned to a published term.

Standards marked catalogue come from the application’s built-in list; their names, publishers, links and namespaces are fixed. Standards marked proposed by AI — verify were added by the model. In both cases the list of reused terms is written by the AI from its knowledge: confirm the terms against the publisher’s documentation before you publish. The application does not look anything up on the internet.

Editing on the diagram

If you can edit the ontology:

  • ＋ Class (top right) adds a class anywhere.
  • Click a box, then in the panel on the right: ✎ Edit (name, definition, parent, module, other names, and metadata — the published term it is aligned to and where it was derived from), ＋ Subclass, ＋ Attribute, ＋ Relationship, or Delete.
  • Click a line or its label in a relationship view to edit or delete that relationship. The pencil next to an attribute or relationship in the panel does the same.

Every change is saved at once as a new version (see Versions), so nothing you try is irreversible. Good to know:

  • Deleting a class also deletes the relationships and attributes defined on it; its subclasses move up to its parent. The confirmation tells you how many are affected.
  • An identifier is made from the name when a class or property is created and does not change when you rename it.
  • The layout is drawn automatically. Boxes cannot be dragged to a new position.

Classes & properties tab

The same content as tables — Classes, Relationships, Attributes, Controlled values, Rules, Modules — with a filter box. Click a class row to open it; use Edit on the other rows. This is the quickest way to review definitions in bulk or to add controlled values and rules.

Changing it with AI

✨ AI › Change it with an instruction: describe the change in plain words (“add co-applicants and guarantors to a loan application”). The AI adds, corrects or removes what is needed and saves a new version; everything else is left untouched.

Use cases

The Use cases tab lists the questions the ontology is meant to answer. Open one to see why it matters, a diagram of exactly the classes, relationships and attributes that answer it, the path through the model step by step, a SPARQL query, and an example answer.

  • Required by the owner — the use cases you listed when creating the ontology.
  • Written by AI — added during the build or with ✨ Write more with AI (you can give a focus, e.g. “risk and compliance questions”).
  • Added by hand — ＋ Add use case. You may tick the classes and properties it uses, or leave them empty and test it.
  • From the test bed — a tested use case saved with “Save as use case”.

🧪 Test this use case takes it to the test bed.

Test bed — does the ontology address a use case?

Type any use case, question or report in your own words and press 🧪 Run test. Viewers can run tests too; a test changes nothing in the ontology.

What you get

  • Coverage — a percentage, and a verdict: Addressed, Partly addressed or Not addressed.
  • Requirement by requirement — the use case is broken into the concepts, relationships, attributes and rules it needs. Each is covered (an element means exactly this), partial (something close exists) or missing, with the elements that are the evidence and the reason.
  • A picture — the classes the use case touches (green outline) and the proposed additions (orange, dashed).
  • Gaps — what is missing and what cannot be answered because of it. If the classes needed are not linked to each other, that is reported as “Not joined up”.
  • Proposed changes — the classes and properties that would close the gaps, as a list you tick (see Choosing proposed changes). Apply selected changes saves them as a new version; then press ↻ Test again to confirm the coverage went up.
  • How it would be answered and a SPARQL query, when it is answerable.

How the score is produced — and why you can rely on it

The AI model does the reading and the matching. The application then checks the model’s claims itself before anything is shown:

  • Every element cited as evidence must exist in the ontology. If it does not, the requirement is marked down and a “Checked:” note says why.
  • A relationship counts as covered only if an actual relationship is cited, an attribute only if an actual attribute or controlled value is cited.
  • Coverage = (covered + ½ × partial) ÷ all requirements. It is calculated by the application, never taken from the model.
  • Addressed means at least 85% with nothing missing; Not addressed means under 40%.
  • Proposed additions that point to something that does not exist are discarded.

What it cannot do: judge whether the breakdown into requirements is the one you had in mind. Read the requirement list — if something you need is not in it, rephrase the use case and test again.

Test again, and why a score can go down

The AI model breaks a use case into requirements anew every time it is asked. A fresh breakdown of the same text can come out different — usually longer and stricter once the ontology has grown, because there is more to compare against — and its percentage is then measured against a different list. That is why a score could fall after you had added the proposed elements, although nothing had got worse.

So there are two buttons on a result:

  • ↻ Test again re-checks the same requirements against the current version. The scores compare like with like, and a green or amber line says, for example, “Re-test of the same 4 requirements: 25% on version 3 → 100% on version 4. 3 improved, 0 got worse.” A Before column shows each requirement's earlier status, with ▲ or ▼ where it changed. If something got worse, the Why column says what the model now finds lacking — typically a definition that became vague or a relationship that was removed.
  • New breakdown lets the model break the use case down afresh. Use it when you have reworded the use case or want a second opinion; its score is not directly comparable with the earlier one.

The tiles above the history summarise the latest result of each distinct use case. Results are kept per version: an older result says “(older)” and offers Test again. Test results are included in the PDF, PowerPoint and Excel downloads.

Answer from your data

When the ontology's knowledge graph is built and you have access to its data sources, the test bed shows Also answer it from the knowledge graph (ticked). The AI then writes a query for the use case — it is given the ontology and the shape of the graph, never the records — and the application checks it and runs it on your data. The result shows:

  • a verdict: Answered from the data (the query returned records), The query found nothing, or The query failed (with the reason; a query the engine rejects is corrected once by the AI, from the engine's message only);
  • in plain words, what the query looks for; and what the data lacks, if the AI finds something missing;
  • No data in the knowledge graph for: … — elements the use case or the query needs that exist in the ontology but have no records or values, because nothing is mapped to them or the columns are empty. This is the usual reason for an empty answer;
  • the rows returned, and the records behind the answer as a picture, one colour per class;
  • the query itself, with Open in the query console to adjust it, and ↻ Run again to run it on the graph as it is now (no AI, so no cost).

An earlier test can be answered afterwards with 🔎 Answer from the knowledge graph. The test history shows the answer in the From the data column. People without access to the data sources see that a test was answered, and the query, but not the records.

Knowledge graph — your ontology filled with your data

The test bed tells you whether the ontology can represent a use case. The knowledge graph goes one step further: it loads your actual records — customers, orders, loans, dealers — into the ontology, so you can see whether your data answers the question, and what the answer is. It is on the Knowledge graph tab of an ontology that uses at least one data source.

1. Map the ontology onto your tables

The mapping says, for each class, which table holds its records; for each attribute, which column; for each relationship, how the tables join; and for each controlled value, which code column holds it. Three ways to make it:

  • Match by names — instant, no AI: tables named like classes, columns named like properties, and the references found when the data source was profiled.
  • ✨ Propose with AI — the AI reads the ontology and the table profiles (the same information it gets for a build) and proposes a full mapping. Anything it names that does not exist — a class, a table, a column — is left out and listed, so a wrong guess never reaches the graph.
  • ＋ Map a class / Edit — the form: choose the class and its table, the column that identifies a record (other tables refer to it) and the one that names it, then a column for each attribute and controlled value, and for each relationship where the link is: a column in this table holding the other record's identifier (a foreign key), a column in the other table holding this record's identifier, or a separate link table. If only some rows of a table belong to a class (for example a type column), set Only some rows of the table are this class.

Proposals are marked draft. Check that the table really holds that class and that the columns mean what the properties say, then press ✓ Confirm. Mappings you confirmed or edited are kept when you ask for a new proposal; proposals add only what is missing.

2. Build the graph

▶ Build the knowledge graph reads the mapped tables — read-only, with queries built by the application — and loads the records. No AI is involved. Each record gets the type of its class and of every parent class, and a name; relationships are stored in both directions where the ontology names an inverse. The build runs in the background with progress at the top.

  • At most 10,000 rows per table are read (an administrator can change this). A table read in part says so; links to rows that were not loaded show as missing.
  • Uploaded datasets are read from the copy kept when they were uploaded. Files uploaded before version 1.7 were not kept: upload them again (same name) before building.
  • Columns that look like personal data are not loaded unless the data source's owner ticks Load personal data into knowledge graphs in its Settings. A record whose name column is personal is shown as, for example, “Customer 17”.
  • The graph is a copy taken at build time. When the data, the mapping or the ontology change, the tab says so — press ↻ Build again from the data.

What is in the graph lists the records per class and the values per property, and everything worth checking: rows without an identifier, repeated identifiers, code values that match none of the ontology's controlled values (with examples), links pointing to records that are not there, values that do not fit their type, personal columns left out. These are usually data-quality findings, or mapping mistakes to correct.

Seeing the graph

Once it is built, the Knowledge graph tab shows it in four ways:

  • The graph at a glance — every class that holds records, with how many, and the relationships between them, with how many links. Click a box to list that class's records in the explorer.
  • Explore records — find a record, see its values and linked records as a picture, and click through from record to record (see below).
  • Ask the graph — a query and a picture of the records behind its answer.
  • Test bed — a use case answered from the data, with the records behind the answer.

For very large graphs or other kinds of pictures, ⬇ Graph (Turtle) loads into graph tools such as GraphDB, Stardog, Neo4j (with its RDF plug-in) or Gephi.

Where the data lives: a copy on this server, or live

Under Where the data lives (people who can edit the ontology and use its data sources):

  • A copy on this server (the default) — building reads the data sources once and keeps the records in the graph's store on this server. Questions are fast; the data is as it was at the last build. Build again, or schedule nightly or weekly rebuilds.
  • Live from the sources — nothing kept on this server — no copy is written. Each time the graph is used — a question in the console, a test-bed answer, a record in the explorer, a download — the application reads the databases at that moment, makes the graph in memory, answers, and discards it. Answers are always current. It is slower (the mapped tables are read each time, up to the row limit per table) and puts load on the databases. Reuse what was read for … minutes keeps a fetched graph in memory, never on disk, so that several questions in a row do not each read the databases; 0 reads for every question.

Switching to live deletes the stored copy and switches off scheduled rebuilds. In live mode the button reads ↻ Read the sources now: it checks that the mapping works and updates the counts shown (the counts and the time of the last read are kept; example values are not). Switching back to a copy needs a build.

Live mode is about databases. Uploaded datasets are themselves files on this server; their owner decides whether a copy is kept at all (Keep a copy of uploaded datasets on this server in the data source's Settings — when off, files are profiled when uploaded and then deleted, and their rows cannot be loaded into a graph). Facts accepted from documents are part of the graph's definition and are kept in either mode.

From documents — judgments, opinions, contracts, policies

Records can also come from unstructured documents: the documents of the ontology's data sources, and the documents added on its own Sources tab. The From documents card lists them. Tick the ones to read and press ✨ Extract with AI.

The AI reads each document (a long one in parts of about 40,000 characters) and lists the entities it states — parties, courts, decisions, provisions, transactions… — with their attributes, and the relationships between them, using only this ontology's classes, properties and controlled values. For every item it must give the exact words of the document that state it. The application then checks every item before you see it:

  • the class, property or controlled value must exist in the ontology, and a relationship must fit (its domain and range, subclasses included);
  • the quoted words must really be in the document — compared without regard to capitals, punctuation or line breaks. An item whose quote is not there is rejected: this is what keeps invented facts out;
  • values are converted to the attribute's type (dates as dates, “Rs. 19,14,55,804” as 191455804); a value that does not fit is kept as text and marked ⚠.

What fails is listed under rejected by the application's checks, with the reason. What the documents state but the ontology has no class or property for is listed under the ontology has no place for — a ready-made list of gaps.

The same thing mentioned in several places becomes one entity. Names are compared after removing differences such as capitals, punctuation, “M/s.”, and “Private Limited” versus “Pvt. Ltd.”; each mention keeps its quote and page. Names that are close but not certain — “High Court at Calcutta” and “Calcutta High Court” — are offered under Possibly the same: Merge, or Not the same. When a later document is read, the AI is told which entities are already known so it reuses them.

Nothing goes into the graph until a person accepts it. Filter by document and status, tick, and ✓ Accept ticked or ✕ Reject ticked; accepting a relationship also accepts the two entities it links. Then build the graph again. Reading a document again replaces what it proposed that was not yet accepted; what was accepted stays. In the graph, every entity keeps its other names and the documents it came from, and answers, the explorer and the console show the document, page and quote behind each record.

The text of the documents is sent to the AI model you choose — use one your organisation allows for that material, or a self-hosted model.

Explore records

Once the graph is built, Explore records finds a record by name (or another name it is known by) and class, and shows its values, the records it is linked to, a picture of them, and — for records from documents — where they come from. Click a linked record or a box in the picture to open it; ← Back returns.

3. Ask it questions

Ask the graph (SPARQL) runs a query and shows the rows and a picture of the records behind them. Pick an example to start from. Queries can only read — a query that tries to change the graph, or to call another server, is refused — and a query that runs longer than 20 seconds is stopped.

In the Test bed, tick Also answer it from the knowledge graph: after checking the ontology, the AI writes a query for the use case and the application runs it on your data — see Answer from your data.

Downloads and scheduled rebuilds

  • ⬇ Graph (Turtle) — the ontology and all its records, to load into a triple store (GraphDB, Stardog, Neptune, Fuseki…). Only for people who may see the records.
  • ⬇ Mapping (R2RML) — the mapping onto tables in the W3C R2RML standard, so other tools can produce the same graph from the databases. Matching code values to controlled values and joins through link tables cannot be said in R2RML; they are written as comments in the file.
  • Rebuild from the data automatically — never, every night (02:00, server time) or every week. The rebuild runs with the access of the person who set it up; if that person can no longer edit the ontology or use its data sources, the schedule switches itself off and the tab says why.
  • Records with it in “What is in the graph” is the share of a class's records that have each property — a quick view of how complete the data is.

Who sees the records

  • Only people who may use every data source the graph was built from see its records — in the console, in test results and in the examples of data problems. Everyone else who can open the ontology sees the mapping and the counts, and is told which data source they would need. Viewers see the design only.
  • Changing the mapping and building need edit access to the ontology and access to its data sources.
  • Query results are never sent to the AI model. To write a query it receives the ontology and the shape of the graph — which classes have records and which properties hold values — not the records.
  • Every query is recorded in the audit log. Delete graph removes the copy of the data; the mapping stays. Deleting the ontology deletes its graph.

Quality, reasoner and gap review

The Quality & reasoning tab has three independent checks.

1 · Modelling checks (no AI)

Run automatically on every change, giving a score out of 100: classes or properties without a definition, classes not connected to anything, groups cut off from the main model, parents with a single subclass, duplicate labels, leaf classes without attributes, relationships without an inverse, naming convention, use cases that reference nothing, modules no use case touches, no standard referenced. Click a class name to open it in the diagram.

2 · Logical test with a reasoner

A reasoner works out everything that logically follows from the ontology and reports contradictions.

ReasonerWhat it isNeeds
Built-in (OWL 2 RL)A rule reasoner. To expose classes that can never have a member, it creates a test member for every class and both ends of every relationship and looks for contradictions.Nothing extra.
HermiT (OWL 2 DL)A complete description-logic reasoner, the one used by Protégé.Java installed on the server. If it is not, the button is greyed out and says so.

They find, for example: a class placed under two classes that a rule says never overlap; a relationship whose two ends cannot both be satisfied; an inverse pair that does not mirror each other. The result also states how much logic there was to test. A reasoner can only test what is stated: add “never overlap” rules (Classes & properties › Rules) and mark properties as mandatory to give it more to check. A reasoner cannot tell you a concept is missing — that is what the test bed and the gap review are for.

The reasoner also proposes the fix. For every contradiction it finds, it lists the concrete changes that remove it — which relationship to change, which rule to adjust or delete, which class to move. Where the right answer is a business decision (for example: is a Store really a kind of Sales channel, or should the rule go?), it shows the options side by side, ticks the recommended one, and lets you pick only one. Apply, run the reasoner again, and it should report “Logically consistent”.

A reasoner can only remove contradictions; it cannot write a missing definition or invent a concept. For that, use the next two.

3 · Fix proposals by a reasoning model

✨ Propose fixes with AI gives an AI model everything the reasoner and the modelling checks found — contradictions, missing definitions, classes without attributes, the absence of “never overlap” rules — and asks for the concrete changes that fix them: what to add, what to change and what to delete, each with the reason in plain language. You can add a note of anything else to attend to. Nothing changes until you choose.

4 · Gap review by a reasoning model

An AI model reads the whole ontology as a critical domain reviewer, lists what is missing or wrong for the scope and the required use cases, and proposes additions, corrections and deletions in the same tick-and-apply list. Choose any configured model — Claude, or a self-hosted model such as Hermes, Llama or Qwen connected through an OpenAI-compatible endpoint (see Administration). Using a different model for the review than for the build gives an independent second opinion.

What you leave unticked stays on offer: after applying some changes, the rest are listed again against the new version, until you run the review again.

Choosing proposed changes

The reasoner, the AI fix proposals, the gap review and the test bed all present what they suggest the same way: a list of separate changes, each one a row you can tick.

ColumnMeaning
ActionAdd a new class, relationship, attribute, value or rule · Change an existing one (the details show old → new for each field that changes) · Delete one.
What changesThe element, written as a reader would say it — “Product — covered by → Warranty (0..1)”.
WhyThe problem or gap it fixes.
  • Dependencies are kept together. A relationship to a new class needs that class: ticking the relationship ticks the class, unticking the class unticks the relationship. Deleting a class also deletes the relationships and attributes defined on it; those rows are linked the same way. A row says what it needs (“Needs: …”) or what goes with it (“Also removes: …”).
  • Alternatives: where two options fix the same problem, they are marked recommended and alternative; ticking one unticks the other.
  • Apply selected changes saves them together as one new version. Every change can therefore be undone from Versions.
  • The server works out the changes again from what it holds at the moment you apply — the browser only says which rows you chose — and every change passes through the same checks as an edit by hand.
  • If the ontology has changed since the proposals were made, they are marked out of date: run the check again.
  • Only people who can edit the ontology can apply; everyone who can see it can read the proposals.

Versions

What is sent to the AI model

When you build, refine, review or test, the chosen AI model receives:

  • the domain, scope, required use cases, requirements and reference notes of the ontology;
  • the text extracted from its source documents, and the structure of its databases (table and column names, types, keys, comments);
  • from data sources: each table's profile — row counts, types, roles, how many values are empty or distinct, ranges, references — your business descriptions, and, where the data source allows it, a few sample values per column and the value lists of code columns (never of columns that look like personal data unless the owner allows it). Statistics are computed on this server;
  • entries from the built-in standards catalogue;
  • the ontology itself; and, in the test bed, the use case you typed;
  • to propose a knowledge-graph mapping: the table profiles, as for a build; to extract facts from documents: the text of the documents you choose, with the ontology; to write a query for the test bed: which classes of the graph have records and which properties hold values — never the records.

It never receives: whole tables or bulk rows (at most the sample values above), the records of a knowledge graph or the results of its queries, database passwords, other ontologies, user accounts, or API keys.

If source documents contain confidential material, choose a model your organisation is allowed to send it to — or a self-hosted model, in which case nothing leaves your network. The application itself makes no other outside connections.

What comes back from a model is never used as it is: it is rebuilt field by field, references to things that do not exist are repaired or dropped, and test-bed scores are computed by the application.
