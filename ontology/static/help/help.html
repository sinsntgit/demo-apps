Getting started

OntoStudio builds an ontology for any domain: a precise, shared description of the things a business deals with (its classes), how they relate (its relationships), what is recorded about them (their attributes) and the rules that hold. It researches the published industry standards for the domain, builds on them, explains the result in plain language, draws it, lists the questions it can answer, and lets you test whether it really covers a use case.

The flow in six steps

  1. Create an ontology: give a domain, your use cases and requirements, a database, or a folder of documents — any one of them is enough. See Creating an ontology.
  2. Build it with an AI model. This takes a few minutes and runs in the background.
  3. Read the Overview and the Standards it was built on; look at the Diagram.
  4. Adjust it — by clicking on the diagram, in the tables, or by telling the AI what to change.
  5. Test it: enter use cases in the Test bed, run the reasoner and the gap review, close the gaps.
  6. Download it as a handbook (PDF), a presentation (PowerPoint), a workbook (Excel) or as OWL / Turtle / JSON-LD / JSON for other systems. See Downloads.

A sample ontology, Sample: Retail order management, is installed with the application so that every screen can be tried before an AI model is set up.

What an ontology is — the words used here

TermMeaningExample
ClassA kind of thing.Order, Customer, Shipment
Subclass (“is a kind of”)A more specific class. It inherits every relationship and attribute of its parent.Store is a kind of Sales channel
ModuleA subject area that groups classes. Each module has its own colour in diagrams.Parties, Product catalogue
RelationshipA named link from one class to another. Read it as a sentence.Order — placed by → Customer
InverseThe same link read the other way round.places ↔ placed by
AttributeA value recorded about a class.Order has order date (date and time)
How many (cardinality)Whether the relationship or attribute is optional or mandatory, and whether there can be several.“exactly one (mandatory)”
Controlled valueOne of a fixed list of allowed values.Order status: Placed, Paid, Shipped…
RuleA business constraint or calculation in a plain sentence. A “never overlap” rule is also checked by the reasoner.A shipment needs a paid order.
Use caseA question or task the ontology must be able to answer (a “competency question”).Which paid orders have not shipped?
Standard / alignmentA published ontology or industry standard the model builds on; a class can be declared the same as, a kind of, or related to a published term.Order = schema:Order

The method follows standard practice in ontology engineering: reuse published vocabularies first, let the use cases decide what must be in the model, check it with a reasoner, and keep every version.

Creating an ontology

In the library press ＋ New ontology. The wizard has four steps; only the name is mandatory, and you may give as little or as much as you have.

1 · Basics

  • Domain — what the ontology is about, in a few words. Leave it blank to let the AI infer it from your documents or database.
  • Scope — what to cover and what to leave out. The more precise, the better the result.
  • Size — Compact (about 15–25 classes), Standard (about 35–55) or Comprehensive (about 70–100; slower and costs more).
  • Folder — where it is kept; see Folders & access.

2 · Use cases & requirements

This is how you get a custom ontology designed around your needs.

  • Use cases it must answer — one per line, in your own words. Each becomes a required use case: the ontology is designed so that it can answer it, it is listed first under Use cases with the label “Required by the owner”, and you can test it with one click.
  • Requirements — anything it must satisfy: regulations, systems it must map to, naming rules, level of detail.
  • Reference notes — your own terms, glossary and abbreviations.

3 · Database & documents

Optional. Ground the ontology in what you already have — see Building from a database or documents.

4 · Build

Choose the AI model and how many extra use cases the AI should write, then press ✨ Create and build with AI. Create empty makes an ontology with nothing in it, to draw by hand on the diagram.

What happens during a build

  1. Reading the source material — database structure and documents.
  2. Researching industry standards — candidates are picked from the built-in catalogue of 65 published ontologies and standards (schema.org, FIBO, HL7 FHIR, GS1, ISO 20022, SKOS, PROV-O and so on); the AI chooses those that fit, says how each is used, and may add others it knows.
  3. Designing the class hierarchy on top of those standards.
  4. Adding relationships, attributes, controlled values and rules.
  5. Completeness review — the draft is read critically against the scope and your use cases, and the gaps found are closed.
  6. Writing the explanation and the use cases.

If a build does not finish, the reason is shown and nothing is lost: press Build again, pick another model, or narrow the scope.

Importing an existing ontology file

⬆ Import file in the library brings in an OWL (RDF/XML), Turtle, JSON-LD or N-Triples file — for example a published standard or a model from Protégé — or a JSON file exported from this application. It becomes a normal ontology that you can extend, test and export. Classes, the hierarchy, properties with their domain and range, labels, definitions and individuals are read; complex logical expressions are not.

Building from a database or documents

Source material can be given in the wizard (step 3) or later on the Sources tab of an ontology. It is read when the ontology is built: after adding or removing sources use ✨ AI › Rebuild from scratch.

Documents or a whole folder

  • Drop files or a folder onto the box, or use Choose files / Choose a folder (sub-folders are included).
  • Supported: PDF, Word, PowerPoint, Excel, CSV, text, Markdown, HTML, JSON, XML, YAML, SQL / DDL scripts, SQLite database files. Up to 25 MB per file and 300 sources per ontology.
  • The text is extracted and kept; the original file is not stored. For spreadsheets and CSV only the headings and the first rows are read, to show the structure.
  • Scanned PDFs (pictures of pages) contain no text and are reported as not readable.
  • A small set of documents is given to the AI in full. A large set is first distilled batch by batch into concepts, relationships, attributes, rules and questions, and the ontology is built from those findings. If the material is too large, the build log names the documents that were not read — nothing is dropped silently.

A database

Three ways, all of which read only the structure — tables, columns, types, keys and comments. No rows are ever read.

  1. Upload a schema script (.sql / .ddl) with the CREATE TABLE statements.
  2. Upload a SQLite file (.db, .sqlite).
  3. Read a live database: choose the type (PostgreSQL, MySQL / MariaDB, SQL Server, Oracle), host, database, user and password. The password is used for that one read and is not stored. A read-only user is enough. The driver for that kind of database must be installed on the server; if it is not, the message says which package the administrator has to install.

The AI models the business meaning, not the storage: a table describing a thing or event becomes a class with a business name, a pure link table becomes a relationship, a lookup table becomes a list of controlled values, a foreign key becomes a relationship, and technical columns are left out. Each class and property keeps a Derived from note naming the table or column it came from, so the mapping back to the database is preserved (it is in the Excel and OWL downloads too).

Reading the result: Overview and Standards

The Overview tab is the complete explanation of the ontology: what it is, its purpose, what is and is not covered, a walkthrough of how to read the model, a paragraph per module, and the design decisions with the reasons behind them. The six tiles at the top open the matching tab. ✎ Edit lets you correct the text; ✨ AI › Rewrite the explanation writes it again from the current model.

The Standards tab shows the published ontologies and industry standards the model builds on: how each is used, which terms are reused, and a table of every class that is aligned to a published term.

Standards marked catalogue come from the application’s built-in list; their names, publishers, links and namespaces are fixed. Standards marked proposed by AI — verify were added by the model. In both cases the list of reused terms is written by the AI from its knowledge: confirm the terms against the publisher’s documentation before you publish. The application does not look anything up on the internet.

Editing on the diagram

If you can edit the ontology:

  • ＋ Class (top right) adds a class anywhere.
  • Click a box, then in the panel on the right: ✎ Edit (name, definition, parent, module, other names, and metadata — the published term it is aligned to and where it was derived from), ＋ Subclass, ＋ Attribute, ＋ Relationship, or Delete.
  • Click a line or its label in a relationship view to edit or delete that relationship. The pencil next to an attribute or relationship in the panel does the same.

Every change is saved at once as a new version (see Versions), so nothing you try is irreversible. Good to know:

  • Deleting a class also deletes the relationships and attributes defined on it; its subclasses move up to its parent. The confirmation tells you how many are affected.
  • An identifier is made from the name when a class or property is created and does not change when you rename it.
  • The layout is drawn automatically. Boxes cannot be dragged to a new position.

Classes & properties tab

The same content as tables — Classes, Relationships, Attributes, Controlled values, Rules, Modules — with a filter box. Click a class row to open it; use Edit on the other rows. This is the quickest way to review definitions in bulk or to add controlled values and rules.

Changing it with AI

✨ AI › Change it with an instruction: describe the change in plain words (“add co-applicants and guarantors to a loan application”). The AI adds, corrects or removes what is needed and saves a new version; everything else is left untouched.

Use cases

The Use cases tab lists the questions the ontology is meant to answer. Open one to see why it matters, a diagram of exactly the classes, relationships and attributes that answer it, the path through the model step by step, a SPARQL query, and an example answer.

  • Required by the owner — the use cases you listed when creating the ontology.
  • Written by AI — added during the build or with ✨ Write more with AI (you can give a focus, e.g. “risk and compliance questions”).
  • Added by hand — ＋ Add use case. You may tick the classes and properties it uses, or leave them empty and test it.
  • From the test bed — a tested use case saved with “Save as use case”.

🧪 Test this use case takes it to the test bed.

Test bed — does the ontology address a use case?

Type any use case, question or report in your own words and press 🧪 Run test. Viewers can run tests too; a test changes nothing in the ontology.

What you get

  • Coverage — a percentage, and a verdict: Addressed, Partly addressed or Not addressed.
  • Requirement by requirement — the use case is broken into the concepts, relationships, attributes and rules it needs. Each is covered (an element means exactly this), partial (something close exists) or missing, with the elements that are the evidence and the reason.
  • A picture — the classes the use case touches (green outline) and the proposed additions (orange, dashed).
  • Gaps — what is missing and what cannot be answered because of it. If the classes needed are not linked to each other, that is reported as “Not joined up”.
  • Proposed additions — the classes and properties that would close the gaps. ＋ Add these to the ontology adds them as a new version; then press ↻ Test again to confirm the coverage went up.
  • How it would be answered and a SPARQL query, when it is answerable.

How the score is produced — and why you can rely on it

The AI model does the reading and the matching. The application then checks the model’s claims itself before anything is shown:

  • Every element cited as evidence must exist in the ontology. If it does not, the requirement is marked down and a “Checked:” note says why.
  • A relationship counts as covered only if an actual relationship is cited, an attribute only if an actual attribute or controlled value is cited.
  • Coverage = (covered + ½ × partial) ÷ all requirements. It is calculated by the application, never taken from the model.
  • Addressed means at least 85% with nothing missing; Not addressed means under 40%.
  • Proposed additions that point to something that does not exist are discarded.

What it cannot do: judge whether the breakdown into requirements is the one you had in mind. Read the requirement list — if something you need is not in it, rephrase the use case and test again.

The tiles above the history summarise the latest result of each distinct use case. Results are kept per version: an older result says “(older)” and offers Test again. Test results are included in the PDF, PowerPoint and Excel downloads.

Quality, reasoner and gap review

The Quality & reasoning tab has three independent checks.

1 · Modelling checks (no AI)

Run automatically on every change, giving a score out of 100: classes or properties without a definition, classes not connected to anything, groups cut off from the main model, parents with a single subclass, duplicate labels, leaf classes without attributes, relationships without an inverse, naming convention, use cases that reference nothing, modules no use case touches, no standard referenced. Click a class name to open it in the diagram.

2 · Logical test with a reasoner

A reasoner works out everything that logically follows from the ontology and reports contradictions.

ReasonerWhat it isNeeds
Built-in (OWL 2 RL)A rule reasoner. To expose classes that can never have a member, it creates a test member for every class and both ends of every relationship and looks for contradictions.Nothing extra.
HermiT (OWL 2 DL)A complete description-logic reasoner, the one used by Protégé.Java installed on the server. If it is not, the button is greyed out and says so.

They find, for example: a class placed under two classes that a rule says never overlap; a relationship whose two ends cannot both be satisfied; an inverse pair that does not mirror each other. The result also states how much logic there was to test. A reasoner can only test what is stated: add “never overlap” rules (Classes & properties › Rules) and mark properties as mandatory to give it more to check. A reasoner cannot tell you a concept is missing — that is what the test bed and the gap review are for.

3 · Gap review by a reasoning model

An AI model reads the whole ontology as a critical domain reviewer, lists what is missing or wrong for the scope and the required use cases, and proposes additions and corrections. Nothing changes until you press Apply these changes. Choose any configured model — Claude, or a self-hosted model such as Hermes, Llama or Qwen connected through an OpenAI-compatible endpoint (see Administration). Using a different model for the review than for the build gives an independent second opinion.

Versions

Every change — a build, an AI instruction, an edit on the diagram, additions from the test bed or the gap review — is saved as a new version with who made it, a note, and what was added, removed and changed.

Restore brings an earlier version back as a new version, so nothing is ever lost.

Folders and access levels

Folders are on the left of the library. ＋ New folder creates one; folders can be nested. Open a folder you own to Rename / move it, Delete it (it must be empty) or set its 👥 Access.

Access levels

LevelCan
Read only (“Can view”)Open, download, run tests and the reasoner.
Can editAlso change the ontologies in the folder, build and refine them with AI, add sources, and create new ontologies and sub-folders there.
OwnerAlso delete, move, and decide who has access. Administrators have this on everything.

How access is decided

  • A new ontology is private: only its owner and administrators see it.
  • Access given on a folder applies to every ontology in it and in the folders inside it. Give it to named people, or to everyone signed in.
  • An ontology can also be Shared with everyone (read only) under ⚙ Settings › Who can see it.
  • A person with the Viewer role is always read-only, whatever a folder grants.
  • An ontology someone else put into your folder can be edited by you, but only its owner or an administrator can delete or move it.

People are added by an administrator under Admin › Users. Ontologies are moved between folders in ⚙ Settings by their owner.

AI usage dashboard

AI usage in the menu shows how much AI work was done: number of AI jobs, model calls, input and output tokens, estimated cost, average time, a chart per day (switch between cost, tokens, jobs and calls), break-downs by kind of work, by AI model and by ontology, and the recent jobs. Filter by period, model and kind; ⬇ CSV downloads the detail.

  • Everyone sees their own usage.
  • Administrators see everyone’s, with a break-down by person and a filter to look at one person.
  • An “AI job” is one piece of work — a build, an instruction, a test, a gap review. A build makes about six model calls (more when many documents are read).
  • Cost is an estimate: the tokens reported by the provider multiplied by the prices entered for each model under Admin › AI models. Keep those prices up to date. Self-hosted models can be given a price of 0.

What is sent to the AI model

When you build, refine, review or test, the chosen AI model receives:

  • the domain, scope, required use cases, requirements and reference notes of the ontology;
  • the text extracted from its source documents, and the structure of its databases (table and column names, types, keys, comments);
  • entries from the built-in standards catalogue;
  • the ontology itself; and, in the test bed, the use case you typed.

It never receives: rows from a database (they are never read), database passwords, other ontologies, user accounts, or API keys.

If source documents contain confidential material, choose a model your organisation is allowed to send it to — or a self-hosted model, in which case nothing leaves your network. The application itself makes no other outside connections.

What comes back from a model is never used as it is: it is rebuilt field by field, references to things that do not exist are repaired or dropped, and test-bed scores are computed by the application.
