Getting started

AskData turns a question written in plain English into a SQL query, runs it on your database and shows the answer as a chart, a table and a short summary. You never need to write SQL, but you can always see it, check it and correct it.

The five-step flow

  1. Pick a data model — the database (or folder of Excel / CSV files) you want to ask about.
  2. Pick an AI model — the model that will write the SQL.
  3. Ask your question.
  4. Check the SQL and the result. Confirm it if it is right, fix it if it is not.
  5. Explore — change the chart, export, or ask a follow-up.

Signing in

Sign in with the email and password your administrator gave you. A password set by an administrator is temporary: you are asked to choose your own straight away. Passwords need at least 10 characters with an upper-case letter, a lower-case letter and a digit.

If your organisation requires two-factor authentication you will be taken through setting it up before you can continue. See Security & 2FA.

Asking questions

Type your question in the box at the bottom of the Ask page and press Enter (Shift+Enter for a new line).

Writing questions that work well

  • Say what you want measured and how to break it down. “Total revenue by product category for 2025” is better than “sales info”.
  • Name the time period. “last quarter”, “since January 2025”, “by month”.
  • Say how many rows you want if it matters: “top 10 customers by revenue”.
  • Use your business's own words if they have been taught to the model under Training (for example “AOV”, “active customer”).
  • One question at a time. Ask the second part as a follow-up.

✨ Rephrase: tidy a question before you ask it

Type your question as it comes — “rev by cat pls” is fine — and press ✨ Rephrase next to Ask. The AI model suggests a clearer wording that names the measure, grouping, filters and period you mean, in the business terms of the data model. Nothing is asked yet. Then choose:

  • Use and ask — ask the suggested wording (you can edit it in the box first);
  • Use this wording — put it in the question box so you can change it further;
  • Keep mine — ignore the suggestion.

💡 You may want to say points out something the model would otherwise have to guess, such as the time period — it never adds a filter or period you did not ask for. Verified questions like yours are found on the server without any AI call; their SQL has been checked, so picking one is the most reliable choice. In a chat, the suggestion takes your earlier questions into account, so “same for last year” becomes a complete question.

To improve a question you already asked, hover over it and press ✨ Rephrase beside it: it is copied into the box with a suggestion, ready to ask again.

Why it saves cost. A rephrase sends a much smaller prompt than a question — table and column names, the titles of business terms and a few similar verified questions, but no column types, documentation text, SQL or data. On the SAP sample it is about a sixth of a full question's prompt (about 900 against 5,400 tokens), and the administrator can let a cheaper model do it. It pays for itself when the clearer question avoids a wasted attempt: a clarifying question, an automatic repair, or a wrong answer asked again. The dashboard shows how often rephrased questions are answered right the first time compared with questions asked as typed, so you can see whether it does.

Follow-up questions

Within one chat the model remembers your last three answered questions and their SQL, so you can say “and by region?” or “only for laptops”. Under each answer you also get suggested follow-ups — click one to ask it.

A chat belongs to one data model. Changing the data model starts a new chat.

When the model asks you something back

If your question is ambiguous or the data model does not contain what you asked for, the model replies with a short clarifying question instead of guessing. Answer it in the same chat.

Review SQL before running

Tick Review SQL before running (top of the Ask page) if you want to see and approve the SQL before anything is run on the database. The answer then stops at the SQL with a Run this SQL button. This is useful on large or expensive databases.

Checking and correcting the SQL

Every answer shows the SQL that produced it and a sentence explaining the approach. The grey line next to “SQL” tells you which AI model wrote it, how long writing and running took, and whether it was auto-corrected or edited by you.

When an answer is wrong: report it

Press ✗ Incorrect (or ✗ No, something is wrong if your account shows results only). Pick what is wrong — the numbers are wrong, something is missing, it includes things that should not be there, wrong period or filter, wrong breakdown or grouping, it answered a different question, or something else — and write briefly why, for example “March should be about 1.2M — returns seem to be counted as sales”.

If your account shows results only

An administrator can set an account to show results only. Answers then show the chart, table and summary and a short sentence on how the question was answered — but no SQL and no Python code, and there is no Review SQL before running, Edit SQL or Fix it. You still say whether each answer is right with ✓ Yes, correct or ✗ No, something is wrong, and your reports reach the data stewards in the same way.

Depending on how your administrator has set things up, feedback from analysts is either used immediately or first sent to a data steward for approval. Feedback from stewards and administrators is always used immediately.

Charts and the chart controls

Every result can be viewed three ways using the buttons at the top right of the result: Chart, Table and Summary. AskData picks a sensible starting view; everything can be changed, and your choice is remembered for that answer.

Measures and categories

This is the one idea that explains all the controls:

  • A measure is a quantity that makes sense to add up or average — revenue, quantity, number of orders, impressions.
  • A category (also called a dimension) is a label that says what a row is about — product name, region, language, month, status.

Numbers that merely identify something are categories, not measures. A product ID, an order number, a postcode or a year should never be totalled — “sum of product IDs” means nothing. AskData recognises these from the column name (names ending in id, key, code, no, number, year, month, week, quarter and similar, holding whole numbers) and keeps them out of the Y axis list and out of totals and averages.

If you want to know how many rows fall in each category, choose Count of rows as the Y axis.

Two measures of very different size

Impressions may be in the hundreds of millions while revenue is in the thousands. On one shared axis the revenue bars would be invisible. If you pick an X axis that repeats (for example region in a result that has one row per region and month), the chart adds those rows together so there is one bar per region. A note under the chart tells you when this has happened. Use Split by to see the breakdown instead.

Predictive questions: forecasts, predictions, segments, drivers, anomalies

AskData can go beyond “what happened” and run a statistical model on your data: project a figure forward, predict an outcome, group similar customers, show what drives a result, or point out what is unusual.

Turning it on

Tick 🔮 Use predictive capability at the top of the Ask page before asking. It is off by default and remembered between visits.

  • Unticked: every question gets an ordinary answer, however it is worded.
  • Ticked: a predictive analysis runs when the question calls for one. Ordinary questions are still answered the ordinary way.

What you can ask

KindExample questionsWhat you get
Forecast“Forecast revenue for the next 6 months” · “Project weekly orders to year end”The figure projected forward with a likely range, and an accuracy check on recent history.
Prediction“Which customers are likely to churn?” · “Predict order value from customer and product attributes”A prediction for every row (including those with no outcome yet), how often it is right, and what influences it.
Key drivers“What drives order value?” · “Which factors explain late deliveries?”The inputs ranked by how much they matter, with the direction of the effect.
Segmentation“Segment our customers” · “Group products into 4 clusters by sales behaviour”Groups of similar items, a profile of each, and which group every item belongs to.
Anomalies“Any unusual days in revenue?” · “Show unusual orders”The periods or rows that stand out, and by how much.

What happens when you ask

  1. The AI model writes the SQL that gathers the data needed for the analysis (for a forecast, the history by month; for a prediction, one row per customer with the outcome and the attributes) and names the method and the columns to use. That is all it does — it never sees the data and writes no analysis code.
  2. AskData runs the SQL on your database, with the usual read-only guard, data filters and masking.
  3. The AskData server prepares the data (feature engineering), fits the model, checks how good it is, and produces the charts, tables and explanation. Nothing is sent anywhere.

Reading the output

Every predictive answer has five parts. Use the Show: tick boxes above it to hide or show each one; your choice is remembered for that answer and used in the PDF.

PartContents
ExplanationThe key figures as tiles, then what was found in plain words: the result, the method used and why, how accurate it is, which inputs were used and which were left out (and why).
ChartsHistory with forecast and likely range; importance of each input; segments on a map; actual against predicted; unusual points marked.
ResultsThe answer as a table: forecast values, a prediction per row, the segment of each row, the unusual rows. Sortable, and exportable as CSV from ⬇ Export.

Amber notes at the top are warnings worth reading: too little history, an incomplete latest period, a result that is “too good” (an input probably contains the answer), or gaps that were filled in.

Below the predictive output, Data used shows the rows the SQL returned (the first 1,000 on screen; the analysis used all of them).

The code that ran

The Code part shows the exact Python script that was executed on the server for this answer, from the rows returned by the SQL to the final figures: data preparation, feature engineering, the models tried, the accuracy check and the final fit. Press Copy to take it away; with the SQL above it, a data scientist can reproduce the result.

The script is one of AskData's own tested routines with your column names and settings filled in. It is not written by the AI model.

Changing the settings

  • Forecast: change Periods ahead and press Update.
  • Segmentation: choose the number of Segments (or Automatic) and press Update.
  • For anything else — different inputs, a different period, another grain — say so in a follow-up question, or use Edit SQL: the analysis re-runs on whatever the SQL returns.

How each method works

KindMethodHow to judge it
ForecastThree methods are tried — Holt-Winters exponential smoothing (trend and seasonality), exponential smoothing of the recent level, and a naive “repeat the last value / cycle”. The most recent periods are hidden, each method forecasts them, and the closest is used. Seasonality is used only with two full cycles of history (24 months for monthly data). Quantities that are never negative are not forecast below zero.Typical error on the hidden periods, and vs naive guess: below 1 means the model beats simply repeating the past. If the naive guess wins, the series has no pattern to exploit — treat the forecast as a rough guide.
Prediction of a categoryLogistic regression and a random forest are both trained; each is scored on rows it has not seen (5-fold cross-validation) and the better one is kept.Accuracy against the Baseline (always guessing the commonest outcome). Balanced accuracy and ROC AUC show whether it can tell outcomes apart; 50% / 0.5 is a coin toss.
Prediction of a numberRidge regression and a random forest, compared the same way.R² (share of variation explained) and typical error against the error of always guessing the average.
Key driversThe prediction model above, then each input is shuffled in turn on held-back rows: the more the result suffers, the more that input matters (permutation importance).Importance is association, not proof of cause. Direction is given where it is clear.
SegmentationK-means clustering on standardised inputs. With Automatic, 2 to 8 segments are tried and the most distinct split is kept.Separation (silhouette score): above 0.5 is strong, below 0.25 means the groups overlap.
Anomalies over timeEach period is compared with the median of its neighbours; it is flagged when more than 5 robust standard deviations away. When the series repeats (such as busier weekdays), each point is compared with the same point in neighbouring cycles, so a normal weekend dip is not flagged.Unusual does not mean wrong — check flagged items against what you know.
Anomalous rowsAn isolation forest scores how easily each row is separated from the rest; at most the top 5% are flagged.

Feature engineering applied automatically: numbers are filled in where missing (median) and put on a common scale; text and category columns become one indicator per value, with rare values grouped; dates become year, month and weekday; time series are placed on a regular grid with gaps filled by straight line. Identifiers, free text, masked columns and columns with a single value are left out, and the explanation lists them.

Getting good results

  • Give it history. A forecast needs at least 6 periods and is far better with two years or more. A prediction needs at least 30 rows with a known outcome; hundreds are better.
  • Leave out the unfinished period. “…up to last month” avoids a half-complete month dragging a forecast down.
  • For predictions, ask for inputs known beforehand. A column filled in only after the outcome (a cancellation reason, a closing date) makes the result look perfect and be useless; AskData warns when it sees this.
  • Be specific about the outcome and the item: “predict whether an order is returned, per order, from channel, region and order value”.
  • If the message says the data is unsuitable, the query's data is still shown — adjust the question or the SQL and try again.
  • Confirm good answers. Pressing ✓ Correct saves the SQL together with the chosen method, so similar questions get the same treatment.

Limits

  • A predictive question may read up to 50,000 rows (an administrator can change this). Models are fitted on at most 20,000 rows, sampled at random when there are more; result tables keep the first 2,000 rows.
  • These are sound general-purpose methods, not a substitute for a specialist model built for one decision. Use the accuracy figures to decide how far to trust a result.
  • Data filters and masked columns apply: you can only model the data you are allowed to see.
  • In a report, a predictive answer is re-fitted on fresh data each time the report is opened or sent.

Summary

The Summary explains in words what the result shows. It looks at the shape of the result and writes the explanation that fits:

If the result is…The summary tells you
A figure over time (by day, month, year…)The total and the average per period, the highest and lowest periods, the change from the first period to the last, how the latest period compares with the one before (with a warning if it looks incomplete), and whether the second half of the period is running above or below the first.

A figure broken down two ways (channel and category)The leader on each side and the single biggest combination.

A plain list with no figuresHow many rows, and how the values in each column are spread.
One rowThe figures themselves.

Rules it follows so the explanation is correct:

  • Only quantities are totalled. Averages, rates, percentages and prices (columns whose names contain words like avg, rate, pct, price, margin) are averaged, never added up.
  • IDs, codes and years are categories, never totalled or averaged.
  • If the row limit was reached, it says the figures are partial.
  • Rows with no value are left out and you are told.

The table under the summary lists every column with its kind (measure, averaged measure, category, date) and its range.

The summary is calculated by the AskData server from the rows. It is not written by the AI model — the model never sees your results. Opening an older chat recalculates its summary with the current rules.

Chats and history

Every question and its result is saved automatically. Your chats are listed down the left of the Ask page, grouped by Today, Yesterday, Earlier this week, and then by month.

  • Open a chat by clicking it. Charts reappear exactly as you left them.
  • Rename — hover over a chat and click ✎. A chat is first named after its opening question.
  • Delete — hover and click 🗑. This removes the chat and its saved results for good.
  • Find — type in the Find a chat box above the list.
  • New chat starts a fresh conversation with no memory of earlier questions.

The History page lists every individual question you have asked, grouped by month, with its status. Search it by words in the question or the SQL; click a row to open the chat it belongs to.

Your chats are private to you until you share them. Administrators and stewards can see questions and SQL in the dashboard's query log for monitoring.

Sharing a chat

Open a chat you started and press 👥 Share chat (top right of the Ask page, or hover over the chat in the list and click 👥). For each user group, role or person choose:

  • Can view — they can open the chat and read the questions, SQL and results, but cannot change it.
  • Can view and add questions — they can also ask follow-up questions inside the chat (their questions are marked Asked by …) and rename it.

Only you can share, un-share or delete a chat you started. A chat you share shows 👥 in front of its name. Chats shared with you appear under Shared with me at the top of the list, with the owner's name and whether you can add questions.

Everyone sees results with their own access. Sharing a chat shares the questions and the SQL, not your rows: each answer someone else asked is run again for the person viewing it, with their data filters and masking. Someone who cannot use the chat's data model sees a notice and none of its content. Excel export of other people's answers is not offered (CSV and PDF export use the rows you are shown).

If your administrator has switched off result storage, chats keep the question and SQL but not the rows; press Run again to fetch fresh results.

Reports

A report brings together results from any of your chats — charts, tables and summaries — with your own headings and commentary, and can be exported to PDF, shared and scheduled.

A report stores the questions, not the numbers. Every time it is opened, each result is run again on the database, so charts, tables, summaries and any live text always show the latest data.

Creating a report

Two ways:

  • In a chat, on any result: ⬇ Export → ＋ Add to a report… and pick a report or name a new one.
  • Reports → ＋ New report, then ＋ Result from a chat and tick as many of your past answers as you like — from different chats and different data models.

The PowerPoint deck

The deck is laid out to fit the content rather than copying the page:

  • A title slide with your company logo, the report title and description, the company, who it was prepared for and when the data was refreshed.
  • Each main heading (Heading 1) becomes a section slide; a sub-heading becomes the small label above the next slide's title. Text blocks become a slide of points.
  • Each result gets a slide with its chart on the left and its key points on the right; a short table (up to 6 rows) sits under the key points on the same slide. Longer tables follow on their own slides, at most 16 rows each, spread evenly, with a note when rows or columns were left out.

  • Predictive answers show their key figures as cards, the main chart beside the explanation, further charts two per slide, and their tables.
  • Every slide carries the logo, the report's header and footer text, the company name and the slide number. The accent colour is taken from your logo.

Sharing

A report is private until its owner shares it. Press 👥 Share and choose Can view or Can view and edit for:

  • User groups — everyone in a group set up by your administrator (for example “Sales leadership”). People added to the group later get access automatically; people removed lose it.
  • Roles — all analysts or all data stewards.
  • Individual people — one or as many as you like.

Sharing a report never widens anyone's access to data:

  • The report is refreshed for the person opening it. A result from a data model they cannot use shows “You do not have access…” instead of data.
  • Their data filters apply. Two people can open the same report and correctly see different numbers. A “🔒 your data filters applied” badge shows when this happens.
  • Masked columns stay masked.
  • Someone with edit rights can add only their own answered questions and cannot change the query behind an existing result.
  • Only the owner (or an administrator) can share, schedule or delete a report.

Reported problems: turning a user's report into training

When someone reports an answer as incorrect it appears at the top of the Review queue with who reported it, what is wrong, their reason and the SQL that ran. Choose one of:

Relationships: how the tables join

The Relationships tab is a map of the data model: which tables join to which, on which columns, and which business things (Customer, Invoice, Material) live where. It holds names and keys only, never row data. When someone asks a question, AskData looks up the tables involved and gives the AI model the join paths between them, so it joins on the right columns - for example kna1.KUNNR = vbrk.KUNRG in the SAP sample.

Where these joins come from. Above the diagram, this panel says what the automatic part was built from - and so why a join might be missing: how many foreign keys the database defines (Excel and CSV files never have any), how many approved examples there are and how many of them join tables, which examples use several tables but whose join could not be read (add those joins by hand), and how many examples are still waiting for approval in the Review queue - their joins are only used once approved.

Joins are read whether they are written as JOIN … ON, JOIN … USING or in the WHERE clause, with or without table prefixes, and also when a column is wrapped in TRIM, UPPER or CAST. Column names are compared ignoring spaces, underscores and case, so Customer Code, customer_code and CustomerCode are treated as the same name. A join that only happens inside a sub-query or EXISTS is not read; add it by hand.

For each suggestion you see the join, the evidence and a confidence score. ✓ Confirm uses it from the next question; Edit lets you change the columns and say how many rows are on each side before confirming; ✗ Reject stops it being used and it is never suggested again (rejected joins are listed at the bottom, with Restore). Joins that come from foreign keys or verified SQL can be rejected too, if they are wrong; their columns cannot be edited.

Rows on each side (N:1, 1:N, 1:1) tells the AI where one side has many rows per row on the other - for example many invoices per customer - so that it totals before joining and does not count anything twice. Leave it on Not sure when you do not know. A join on several columns (a composite key, such as company code + document number + fiscal year) is added with ＋ Another column pair.

Business entities. ＋ Add entity records a business thing, the words people use for it, and the table that holds it - for example Customer, also called client, sold-to party, account, stored in kna1 with the key KUNNR. When a question uses one of those words, the AI is told which table holds it and how to join to it - useful where table and column names are cryptic, as in SAP.

The relationships are kept up to date by themselves: after a schema sync, and whenever a verified example is added, approved, corrected or removed, the automatic part is worked out again on the next question. Your decisions - confirmations, rejections, edits, your own joins - are never overwritten. ⟳ Rebuild does the same on request. Every change is recorded in the audit log.

Use a read-only database account

AskData refuses anything that is not a single SELECT, but the database account should also be unable to change anything. Create a dedicated account with SELECT on just the schemas you want exposed:

-- PostgreSQL
CREATE ROLE askdata LOGIN PASSWORD '…';
GRANT USAGE ON SCHEMA public TO askdata;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO askdata;

-- MySQL / SingleStore
CREATE USER 'askdata'@'%' IDENTIFIED BY '…';
GRANT SELECT ON mydb.* TO 'askdata'@'%';

-- SQL Server
CREATE LOGIN askdata WITH PASSWORD = '…';
USE mydb; CREATE USER askdata FOR LOGIN askdata;
ALTER ROLE db_datareader ADD MEMBER askdata;

-- Oracle
CREATE USER askdata IDENTIFIED BY "…";
GRANT CREATE SESSION TO askdata;
GRANT SELECT ON sales.orders TO askdata;   -- repeat per table, or use a role

-- Snowflake

Combined data models: two or more data models together

Some questions need data from more than one system: “Which of our top SAP customers have the most open CRM tickets?” A combined data model puts two to four data models (up to six if an administrator allows it) side by side and records which fields mean the same thing in each — the matches, such as SAP's customer number KUNNR and the CRM's sap_no. Each data model keeps its own training, access and filters.

Once its matches link every data model, it appears on the Ask page like any other data model — see Asking across data models below.

Creating one

  1. Data models → ＋ Combined data model (administrators and stewards).
  2. Give it a name and pick the data models. Each gets a short name (sap, crm) that is put in front of its table names, so sap.kna1 and crm.accounts can never be confused.
  3. Decide whether to Check values to confirm matches (below), then Create and find matches.

Combined data models cannot contain other combined models. A person can use one only if they have access to every data model in it; each data model's row filters and masked columns still apply to them.

Matches

🔗 Matches opens the list of matches. AskData suggests them from the column names, the descriptions in each data model's training (a description of sap_no that mentions KUNNR counts), which columns are keys, and their types. A suggestion is never used until a steward confirms it. A rejected suggestion is not suggested again; Restore brings it back. ＋ Add match records one by hand.

Every match has a key rule, applied to both sides before the values are compared — because systems rarely store a key the same way:

The data model is linked (a green badge) once confirmed matches connect every data model to the others.

Checking values

Names can mislead, so a match can be checked against the data: Check values reads the distinct values of the two columns (up to 10,000 each), applies the key rule and reports how many exist on the other side, for example “100% of crm.accounts values exist in Sample: SAP Sales & Finance”. It also works out whether each side is one row per value (1:1, N:1…).

  • It is off by default and switched on per combined data model (Edit → Check values to confirm matches). When on, ⟳ Find matches also checks the most likely suggestions and drops those whose values hardly overlap (under 5%).
  • It runs on this server only. Values are never sent to the AI model and never stored: only the percentages and counts are kept. For masked columns only the percentages are shown.
  • It runs with the row filters of the person who presses the button, read-only, with the normal query time-out.

Asking across data models

Pick the combined data model on the Ask page and ask as usual. Instead of one SQL query, the AI writes a plan:

  1. One step per data model — for example net sales per customer from SAP, and open tickets per customer from the CRM. Each step runs on its own data model exactly like a normal question: the read-only check, your data filters for that data model, and its masked columns all apply.
  2. A combine step that joins the step results on the AskData server, using the confirmed matches and their key rules (so SAP's 0000100001 meets the CRM's 100001). It can read the step results and nothing else.
  • Each step's tab shows its data model, how many rows it read and whether your data filters were applied. ✎ Edit plan lets you change any step or the combine query and run it again.
  • The AI model never sees data from either system: it gets the same schema and training notes as for each data model on its own, plus the list of matches.
  • Row limits: a step that would read more than the limit, or steps that together read more than the total, stop with a clear message instead of an approximate answer. Ask for totals (per customer, per month) rather than detail.
  • Warnings appear above the result when no rows matched across the data models (check the key rule) or when the key repeats on both sides, which can count rows more than once.
  • Shared chats, reports, PDFs, PowerPoint and scheduled emails re-run the plan with each viewer's own access, as for any answer. People set to see results only never see the plan.
  • Not yet: confirming an answer across data models does not add it to training (it is recorded), and reported problems on these answers are not yet in the stewards' review queue.

How filters are enforced

  • The server applies them, not the AI model. Before any query runs, every mention of a filtered table is swapped for “that table, limited to the allowed rows”. This happens for model-written SQL, SQL the user edits by hand, and reports.
  • The SQL shown to the user stays as written; a “🔒 Your data filters are applied” badge appears on the result.
  • If several filters on the same table apply to someone (say one for their role, one for a group they belong to and one for them personally), they must satisfy all of them. Someone in two groups that each have a filter on the same table sees only rows allowed by both.
  • A group filter follows membership: it applies to people while they are in the group.
  • Administrators are never filtered.
  • A filter removes rows from the table it names. Queries that join to that table inherit the limit through the join — orders joined to North-only customers give North-only orders. A query on orders alone is not limited by a filter on customers; if orders must be limited too, add a filter on orders (for example region_code = 'N').
  • A query the server cannot analyse with certainty is refused for filtered users rather than run unfiltered.
  • Conditions are checked when saved: they must be a single condition, with no sub-queries.

Every filter change is recorded in the audit log.

Companies: several separate companies on one installation

One AskData installation can serve several companies. Each company is fully separate: its own users, user groups, data models and their training, chats, reports, schedules, data filters, settings, email log and audit log. Nobody in one company can see or reach anything of another company — the server checks the company on every request, and tests prove it.

Every person belongs to exactly one company (an email address cannot be in two). The company's name — and its logo, if it has one — appears at the top of the menu.

A platform administrator can give or take away this right under Admin → Users (Platform administrator, for administrators only).

Adding a company

  1. Admin → Companies → ＋ Add company. Enter the company name and the email and name of its first administrator.
  2. Keep Add the sample data models ticked to give them the Retail, SAP and CRM samples and the SAP + CRM combined model to try.
  3. Pass the one-time password shown to their administrator securely; they choose their own at first sign-in.
  4. Give the company an AI model: share one (below), or let their administrator add their own key under AI models.

Edit renames a company, uploads its logo, or makes it inactive: all its people are signed out at once and cannot sign in until it is active again; nothing is deleted. You cannot suspend your own company. ↺ next to an administrator gives them a new temporary password (for a company that is locked out).

Adding people to a company

＋ User on a company's row adds a person straight into that company — analyst, data steward or administrator, and for analysts whether answers show results only. Pass the one-time password shown to them securely. A company's own administrator can also add people under Admin → Users; they always join that administrator's company.

Moving a person to another company

People… lists a company's people with their role and how many reports they own. Move… moves one of them to another company, with the role (and, for analysts, the view) they will have there.

  • They are signed out. Next time they sign in, they are in the new company and see only its data models, chats and reports.
  • Everything that tied them to the old company is removed: their user-group memberships, personal data-model access, personal row filters, chats and reports shared with them personally, and their place on report schedules.
  • Their reports stay with the old company. You choose one of its administrators to take them over. Any schedule on those reports is paused, because the new owner's access may differ: the new owner checks the report and switches the schedule back on.
  • Their chats stay with the old company (with their history and audit records) and are no longer visible to them. Nothing is deleted.
  • You cannot move the last active administrator of a company (add another first with ＋ User), and you cannot move your own account.
  • The move is written to the audit log of both companies.

Sharing AI models and email senders with companies

Under AI models and Email senders, a platform administrator has an extra section, Platform models — shared with companies (and Platform senders). Add a shared model there, then press Companies… and tick the companies that may use it — or All companies, which includes companies added later.

  • Companies use a shared model without ever seeing its API key, URL or server details. Its use is counted in each company's dashboard and in the AI spend column under Companies.
  • A company's administrator can switch a shared model or sender off for their company, add their own, and choose their company's default.
  • Names never clash: within what one company sees, every model (and sender) name is unique. A company cannot add a model named like a shared one it is offered, and a shared model cannot be offered to a company that already has one with the same name — you are asked to choose another name. In the Ask page the picker groups them as Your company and Shared.

PowerPoint template

Upload the company's corporate template (.pptx or .potx, at most 25 MB) under Admin → Companies → Edit, or — as the company's administrator — under Admin → Settings → Company. From then on, report PowerPoint exports for that company are built on it: its slide masters and backgrounds, theme colours and fonts, and slide size (16:9 or 4:3). The template's Title Slide, Section Header and Title Only layouts are used (or the closest ones it has); any sample slides in the template are left out, and placeholders that would stay empty are removed. Remove the template to go back to the built-in design.

Company logo

A company's administrator uploads the logo under Admin → Settings → Company (a platform administrator can also do it from Companies → Edit). PNG, JPEG or WebP, at most 512 KB; SVG is not accepted because it can carry scripts. The logo is shown at the top of the menu for everyone in that company and at the top of every page of the company's report PDFs.

Users and settings

Users

Admin → Users → Add user. Enter the email, name and role. You are shown a one-time temporary password to pass on securely; the user must replace it at first sign-in.

What answers show (analysts only): Results, SQL and code (the default) or Results only — no SQL or Python code, for business users who only need the numbers. Results-only users see the chart, table and summary, and can still mark answers correct or report what is wrong. The server leaves the SQL and code out of everything it sends them — answers, chats shared with them, reports, PDFs and exports — so it is not merely hidden on screen. Data stewards and administrators always see SQL and code, because they review and fix it. The Users list marks these accounts results only.

Audit log

Admin → Audit log records who did what and when: sign-ins (successful and failed), questions asked, SQL edits, feedback, training changes, report opening, sharing and scheduling, data-access and data-filter changes, user-group and email-sender changes, test emails, connection, user, model and setting changes. Filter by event type, search, and export to CSV.

The dashboard

The dashboard shows how well the system is performing and how it is being used. Filter by period, data model, AI model and user using the boxes at the top right.

Query log

Every question ever asked, newest first. Filter by status or feedback, or search. Click a row to see everything about it: who asked, the SQL (and the model's original if the user edited it), the result, the user's note, token counts, and a line stating how many table definitions, examples and document passages were sent to the model.

Using it to improve: filter the log to Incorrect, Corrected and Error. Each is a gap in training — add a note or an example and the same question will work next time.

Installation and operations

Requirements

  • Python 3.11 or newer (developed and tested on 3.13), or Docker.
  • Network access from the server to your databases and to the AI model provider.
  • A modern browser. Nothing is installed on users' machines.

Install and run

From the text2sql folder. A virtual environment keeps AskData's packages separate from other Python software on the machine.

# Windows (PowerShell)
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt -r requirements-drivers.txt
python -m uvicorn app.main:app --port 8000

# macOS / Linux
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-drivers.txt
python -m uvicorn app.main:app --port 8000

Open http://localhost:8000. To let other machines connect add --host 0.0.0.0.

requirements-drivers.txt holds the database drivers. You may remove the lines for databases you do not use.

First sign-in

On the very first start an administrator account is created. Unless you set the variables below, the email is admin@example.com and a random password is printed once in the server window.

Docker

cp .env.example .env      # then edit .env and set T2S_SECRET_KEY
docker compose up --build

This starts AskData on port 8000 with a PostgreSQL database for its own records.

Going to production

  • HTTPS: put AskData behind a reverse proxy (nginx, IIS, a cloud load balancer) that terminates TLS, and set T2S_COOKIE_SECURE=1.
  • Metadata store: use PostgreSQL rather than SQLite.
  • One process per instance. Scale by running more instances against the same PostgreSQL store.
  • Turn on mandatory 2FA in Admin → Settings.
  • Read-only database accounts for every data model.

Backup and restore

Back up two things: the data folder (or the PostgreSQL metadata database, plus the files sub-folder of the data folder) and the secret key. To restore, put both back and start the server. To move servers, copy both across.

Upgrading

Back up first. Replace the application files, reinstall requirements, restart. New tables are created automatically.

Resetting everything

Stop the server and delete the data folder. The next start creates a fresh, empty installation. This erases all users, connections, training and history.

Frequently asked questions

Can AskData change or delete my data?
No. Only single SELECT statements are run, connections are opened read-only where the database supports it, and you should give it a read-only account as well.

Does the AI provider see my data?
It sees questions, table and column names and your training notes. It never sees query results. See What the AI model sees.

Why did the same question give different SQL today?
Models are not perfectly repeatable, and training may have changed. Confirming a good answer as Correct pins it as an example, which makes that question consistent.

Why is a number column not offered on the Y axis?
It looks like an identifier, code or period (see Charts). It is still available as the X axis, in Split by, and with Count of rows. If it really is a quantity, ask the question so the column gets a clearer name — “…as total_units”.

Can I ask across two data models at once?
No. A question runs against one data model. If two sets of data need combining, an administrator can expose them through one database connection.

How fresh is the data?
Live. Every question runs on the source at that moment. Reopening a saved chat shows the result as it was; use Edit SQL → Run to refresh.

Can I share a result?
Put it in a report and share that, or export it as PDF, Excel, CSV or PNG. Chats themselves are private to each user.

Does it work in other languages?
You can ask in any language the chosen AI model understands. Training notes in the same language as the questions work best.
